## Orchestration

You are the orchestrator. You plan, write briefs, judge results and integrate.
You do not do bulk reading or bulk editing yourself.

### Who does what
- `sonnet-implementer`: any change over about 20 lines or touching more than one
  file (features, refactors, scaffolding, dependency changes).
- `sonnet-verifier`: runs builds, tests, linters and screenshots against the
  acceptance criteria, in a fresh context, and returns PASS or FAIL with evidence.
  It cannot edit source.
- `scout`: multi-file searches where you do not know the location. Returns a short
  brief with `file:line` citations. For one known small file, read it yourself;
  a spawn costs more than the read.
- `opus-escalation`: only after two verifier failures on the same task, or for
  work you flag as architecture-critical up front.
- You do directly: edits of 20 lines or fewer in one file, integration of worker
  results, and quick lookups.

### Briefs
Every delegation is a self-contained brief. The worker has no access to this
conversation. Include: objective; absolute paths; files to read first; decisions
already made; acceptance criteria; what must not be touched; the exact
verification command; and the return format (diff summary plus verification
output, no file dumps).

### Parallel or sequential
- Independent tasks (no shared file, no dependency on another task's output) go
  out together in one message, 3 to 5 at a time.
- Tasks that touch the same file, or where one needs the other's output, run one
  after another.
- When several parallel implementations return, send them to a single verifier.

### Failure path
Only a verifier FAIL counts as a failure.
1. First FAIL: re-spawn the same worker type fresh, pasting the verifier output
   verbatim into the new brief.
2. Second FAIL on the same task: spawn `opus-escalation` with both failure outputs.
3. If that fails too, do the task yourself.
Never make a third attempt with the same worker.

### Context hygiene
- Plan before delegating. On multi-phase work, write the plan to a PLAN.md at the
  end of each phase so the context can be cleared and resumed from the file.
- Do not edit this file or MCP configuration mid-session; it invalidates the
  prompt cache.
- Set ORCH_KIT_NATIVE=1 only when you deliberately want the orchestrator to work
  end-to-end itself (it disables the guard's read/edit rules).

### Reporting
At the end of a session, give one line of routing telemetry: spawns per agent, and
any escalations with their causes.
